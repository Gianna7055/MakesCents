# Makes Cents Schema: v2 → v3 Change Log

| # | Change | v2 | v3 | Why |
|---|--------|----|----|-----|
| 1 | `budget` table | One row per user per month (`user_id`, `month_id`, `year`, `budget_name`) | Persistent entity — just `budget_name`. Month data moved out, user ownership moved to `budget_users` | A budget needed to outlive a single month and support more than one user, so it couldn't keep owning month/year/user directly |
| 2 | `budget_users` table | Didn't exist | New join table: surrogate `Id` PK, unique `(BudgetId, UserId)` | Many-to-many access to a budget — multiple people on one budget, or one person on multiple budgets (e.g. a parent viewing a child's budget) |
| 3 | `budget_month` table | Didn't exist (this data lived on `budget` itself) | New table: `budget_id`, `month_id`, `year`, unique `(BudgetId, MonthId, Year)` | Takes over the "one specific month" role that `budget` used to play, now that `budget` itself is persistent |
| 4 | `envelope` table | Single table, `is_sinking_fund` flag distinguished the two kinds | Removed entirely, replaced by `sinking_fund_envelope` and `rollover_envelope` | Sinking funds and rollover funds behave too differently (permanent vs. flexible) to safely share one table long-term, especially once budget templates are involved |
| 5 | `sinking_fund_envelope` table | N/A (was rows in `envelope`) | New table, persistent, tied to `envelope_category_id`. Holds `planned_amount`, `remaining_amount`, `goal_amount`, `goal_end_date` | Sinking funds are guaranteed to exist by template rules, so a single persistent row with a live balance is safe |
| 6 | `rollover_envelope` table | N/A (was rows in `envelope`) | New table, persistent, tied to `envelope_category_id`. Holds **only** `envelope_name` and `transfer_envelope_id` — no dollar amounts | Rollover funds are flexible month-to-month, so the "concept" of the envelope needs to be stable even in months it isn't active — dollar amounts can't live here or they'd be meaningless in inactive months |
| 7 | `rollover_envelope_month` table | Didn't exist | New table: links `rollover_envelope_id` + `budget_month_id`, holds that month's `planned_amount` and `remaining_amount` | Solves the problem of `planned_expense` needing a stable target — the persistent `rollover_envelope` never changes, while this table captures the "was it active, and what was its balance" per month |
| 8 | `envelope_category` | Tied to `budget_id` | Same shape, but `budget_id` now points at the persistent budget | Categories must be stable across months since sinking fund envelopes (which persist) hang off them |
| 9 | `account` | Tied to `budget_id` | Unchanged | Bank/debt/investment accounts don't reset monthly — no reason to move them |
| 10 | `transaction` | Tied to `budget_id` | Tied to `budget_month_id` | Transactions happen within a specific month, unlike accounts or paychecks |
| 11 | `paycheck` | Tied to `budget_id` | Unchanged | It's a recurring definition (like `planned_expense`), not a monthly event — stays persistent |
| 12 | `paycheck_split` | Single `envelope_id` FK | Dual nullable FK: `sinking_fund_envelope_id` OR `rollover_envelope_month_id` | Needs to point at either envelope type, and needs an actual balance to allocate against, so it targets the monthly rollover instance, not the persistent definition |
| 13 | `transaction_split` | Single `envelope_id` FK | Dual nullable FK: `sinking_fund_envelope_id` OR `rollover_envelope_month_id` | Same reasoning as `paycheck_split` — plus now also carries envelope-to-envelope transfers (see #15) |
| 14 | `planned_expense` | Single `envelope_id` FK | Dual nullable FK: `sinking_fund_envelope_id` OR `rollover_envelope_id` (the **persistent** definition, not the monthly instance) | A recurring expense must stay valid into future months that don't have a `rollover_envelope_month` row yet — pointing at the definition instead of an instance keeps the FK stable regardless of which months actually activate that envelope |
| 15 | `transfer_transaction` | Handled both account-to-account and envelope-to-envelope transfers, with `transfer_from/to_envelope_id` columns | Handles **only** account-to-account transfers now. Envelope-to-envelope movement is expressed as two opposite-signed `transaction_split` rows instead | You wanted any envelope able to transfer to any other envelope. Modeling that on `transfer_transaction` directly would have needed 4+ nullable envelope columns and a complex CHECK; reusing `transaction_split` (which already needs to support both envelope types) handles all four sinking/rollover combinations with zero new columns |
| 16 | `transfer_transaction` CHECK constraint | Checked `transfer_transaction_type_id = 1` (Account) / `= 2` (Envelope) | Checks `= 2` (Account) / `= 3` (Envelope) | Bug fix — the enum seeds `Unknown = 1`, `Account = 2`, `Envelope = 3`; the v2 CHECK was off by one against its own enum table |
| 17 | Join-table PK style (`budget_users`) | N/A | Surrogate `Id` + unique constraint, not composite `(BudgetId, UserId)` | Matches your existing DAO base class pattern (`GetById`, `Update`, `Delete` all assume a single-column `Id`), and leaves room for something to reference a specific membership row later (e.g. an audit log, if `Role` gets added) |
| 18 | `is_sinking_fund` column | Present on `envelope` | Removed | Redundant once the physical table split does the same job the flag used to do |

**Not yet decided / explicitly deferred:**
- `Role` column on `budget_users` (you said not needed right now)
- Cross-table envelope name uniqueness (sinking vs. rollover, same category) — still an application-layer check, not enforceable in DDL
- The two-row "opposite signs summing to zero" rule for envelope transfers in `transaction_split` — also application-layer
